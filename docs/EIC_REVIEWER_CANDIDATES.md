# Private Reviewer candidates

These endpoints are an EIC-only preparation workflow, not Reviewer distribution. They require the previously configured Batch 38 proof storage and signing configuration, existing source provenance evidence, and migration 023 applied to the intended database after review and backup. Do not apply a migration to persistent data merely to run tests.

With bearer authentication, an EIC submits a multipart file to `POST /eic/manuscripts/{id}/reviewer-candidates` with `review_round`, `source_id`, positive `artifact_version`, and lowercase `fmt` (`pdf`, `docx`, `doc`, or `txt`). The supplied filename is ignored. The file must differ from the approved source snapshot. This check cannot establish anonymity. The server reserves an opaque identifier, stores bytes in the configured private proof-storage directory, and rechecks the active source proof before recording private storage. A failure can leave a reservation and possibly a private file; reconcile manually before retrying. Existing files and reservations are not automatically removed.

An EIC can retrieve the private candidate for human inspection at `GET /eic/manuscripts/{id}/reviewer-candidates/{candidate_id}/content`. The neutral download filename is not evidence of anonymity. After reviewing all applicable material, an EIC submits all ten explicit true checklist fields to `POST .../{candidate_id}/verify`: `author_names`, `affiliations`, `contact_information`, `document_metadata`, `word_comments`, `revision_history`, `headers_footers`, `hidden_text`, `figures_supplements`, and `acknowledgements_references`. The attestation is bound to the candidate's recorded digest and version; a true value means the item was reviewed, including a determination that it was not applicable when appropriate. It is a human attestation, not an automated guarantee.

`POST .../{candidate_id}/approve` records a separate EIC approval only after the checklist and byte/proof verification. `POST .../{candidate_id}/withdraw` appends an idempotent withdrawal. Neither operation by itself inserts a Reviewer artifact binding or makes the file downloadable by a Reviewer. No historical approvals are backfilled. Proof key rotation and orphan reconciliation remain the limitations described in `EIC_PROSPECTIVE_PROOFS.md`.

Batch 41 adds separate EIC operations `POST .../{candidate_id}/publish` and `POST .../{candidate_id}/bind/{assignment_id}`. Publication links the already private, verified and approved candidate to the existing artifact evidence ledger; binding requires a current accepted assignment and locked Double Blind policy. Both are idempotent for the same record. The existing Reviewer download uses a Main-owned guard for these bindings and rechecks the active source proof, candidate verification and approval, withdrawal, assignment and file digest on each request. The candidate withdrawal endpoint and `POST .../{candidate_id}/withdraw-artifact` are distinct; either blocks subsequent candidate-backed reads. This is a human attestation, not an automated guarantee of anonymity.

`GET /eic/manuscripts/{id}/reviewer-candidate-reconciliation` is an EIC-only dry-run report of known reservations and storage entries. It reports recorded candidate-file ownership, approximate age, digest verification and known staging entries. It does not enumerate every unreferenced file, persist an audit record, or remove anything. Manual ownership, age and reference checks are required before any separately authorized cleanup.

Migration 024 adds an append-only publication audit. New candidate-backed publication, binding and download require this migration; it must be applied only to an explicitly selected database after backup and review. An EIC can call the publication endpoint again to reaffirm a previously published candidate lacking a 024 record. The reaffirmation receives its actual current timestamp and does not invent a historical event. Downloads do not yet have a durable delivery audit; an HTTP server accepting a response is not proof that a client received it.
