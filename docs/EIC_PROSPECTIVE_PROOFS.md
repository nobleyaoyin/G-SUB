# Prospective EIC source attestations

This endpoint records an EIC's prospective self-attestation. It does not independently establish that a document is anonymous, create the separately prepared Reviewer artifact, or enable Reviewer downloads. Existing Double Blind delivery continues to fail closed without the separate artifact evidence and authorization.

Apply migration `migrations/022_eic_prospective_proof.py` using the project's migration procedure against the intended database only, after backup and review. Do not apply it to existing data merely to run tests. Configure the server with `GSUB_EIC_PROOF_PRIVATE_ROOT`, `GSUB_EIC_PROOF_KEY_ID`, and `GSUB_EIC_PROOF_SECRET`. The root must already exist, be private and canonical, and not overlap application data. Generate a unique random 32-byte secret and supply its lowercase hexadecimal representation through protected server configuration. Keep it stable and protect backups; losing or changing the key or key ID makes existing proofs unverifiable. This implementation does not yet provide key rotation or multiple verification keys. Never commit the secret.

After author confirmation, a current review round and its authoritative source binding must already exist. An authenticated active EIC may obtain the binding ID from the EIC manuscript overview. With Double Blind selected, `POST /eic/manuscripts/{manuscript_id}/prospective-proofs` accepts `review_round`, `source_id`, and three explicit true values: `identity_removed`, `identifying_metadata_removed`, and `manual_review_completed`. The server reads and hashes the current bound source itself. It does not accept a caller-supplied proof or digest. A successful response contains the server-generated proof ID and metadata.

`GET /eic/manuscripts/{manuscript_id}/prospective-proofs/{proof_id}?review_round=...&source_id=...` verifies the active proof without returning document bytes. An active EIC can revoke it with `POST /eic/manuscripts/{manuscript_id}/prospective-proofs/{proof_id}/revoke` and a nonempty `reason`; repeating revocation is safe. Current policy permits an active EIC to act on nondraft manuscripts, rather than assigning manuscripts to individual EICs.

Approval uses an append-only durable storage reservation before private publication, followed by revalidation and a separate transaction that commits the signed proof. If publication or the final commit fails, no valid proof is created, but a reservation and possibly an inaccessible private snapshot can remain for operator reconciliation. Do not blindly remove these records or retry an uncertain operation without checking them. Proof verification checks the signed evidence, source and policy, as well as the stored snapshot. One source can have only one proof, even if revoked; reapproval of the same source is not implemented. Historical approvals are not backfilled.

An authenticated active EIC can link an existing valid proof into the artifact pipeline's source evidence with `POST /eic/manuscripts/{manuscript_id}/source-provenance-evidence`, supplying `source_id` and `expected_revision`. The server verifies the proof and private snapshot and records the evidence in the existing schema. This does not prepare, approve or publish a Reviewer artifact and grants no document access. The internal candidate check rejects byte-identical source files, but a different digest does not establish anonymity. A separately prepared and reviewed artifact and a trusted download context remain required.
